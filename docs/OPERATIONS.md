# 운영 안내

서버에 설치해 운영할 때 필요한 설정, 명령, 화면별 동작입니다. 소개와 구조는 [README](../README.md)에 있습니다.

KT Cloud 작업공지 수집 → 고객별 안내 → NCP SENS 발송(`sens.env`가 있을 때) → 사내 발송 사본 확인.

- 다른 서버로 옮기기: [MIGRATION.md](MIGRATION.md) (`ops/migrate/`)

## 서버 배치

| 경로 | 용도 | git |
|---|---|---|
| `/data/csp-notice/app` | 코드 저장소 (원격: GitHub `OWNER/notice`, 코드, 문서만). 개발은 여기서 | 포함 |
| `/data/csp-notice/release` | 운영 코드. systemd가 실행하며 `ops/deploy.sh`로만 갱신 | 커밋된 코드의 사본 |
| `/data/csp-notice/var` | DB, 수집 상태, 수동 수집 요청 파일 (`cspnotice` 소유) | 제외 |
| `/data/csp-notice/backup` | 매일 밤 DB 백업, 14일 보관 (백업 직후 1년 지난 데이터 삭제) | 제외 |
| `/data/csp-notice/private` | 실제 고객정보 CSV, 엑셀 원본 (root 0700) | 제외 |
| `/etc/csp-notice/pop3.env` | 메일 접속 정보 (root:cspnotice 0640) | 제외 |

서비스는 로그인할 수 없는 시스템 계정 `cspnotice`로 실행합니다. 코드, systemd 유닛, 설정은 `/root`나 개인 계정 경로를 참조하지 않습니다.

## 개발 환경

Python 3.12 가상환경은 `/data/csp-notice/venv`에 있습니다 (시스템 Python 3.6, 3.9는 사용하지 않음).

```bash
/data/csp-notice/venv/bin/pip install -r requirements-dev.txt   # 패키지 설치
/data/csp-notice/venv/bin/python -m pytest                       # 테스트 (가짜 POP3 서버, 실제 메일 접속 없음)
```

## 웹 화면

주소: `http://192.0.2.10/` (사내망 전용, Proxmox가 외부 접근 차단). nginx(80) → gunicorn(127.0.0.1:8001, `csp-notice-web.service`).

메인 아이디 하나로 함께 씁니다. 담당자 확인, 발송 기록 등에서 이름을 적으면 이력에 그 이름이 남고, 마지막에 적은 이름은 이 브라우저에 기억돼 다음 이름 칸에 미리 채워집니다. 오른쪽 위 Light/Dark로 화면 테마를 고릅니다(고르기 전에는 PC 설정을 따름).

계정은 두 종류입니다(사용자 2026-10-22). **관리 계정**(`is_staff`)만 환경 설정(자동 발송 ON/OFF, KT 공지 양식), 고객 정보(추가, 수정, 운영 DB 조회, 사내/안 쓰는 계정, 사내 고객명), 받는 사람 그룹을 바꾸고 /admin/에 들어갑니다. 함께 쓰는 **메인 아이디**는 그 화면들을 보기만 하고(제목 옆 '보기 전용'), 안내 복사, 발송하기, 담당자 확인 같은 일상 업무는 그대로 합니다. 관리 계정은 비밀번호를 정할 사람이 직접 만듭니다(아래 명령, 묻는 대로 아이디와 비밀번호 입력). 메인 아이디를 일반 계정으로 바꾸는 것은 관리 계정이 생긴 뒤에 합니다: `manage.py shell -c "from django.contrib.auth.models import User; User.objects.filter(username='<메인 아이디>').update(is_staff=False, is_superuser=False)"`.

- 작업 공지: 작업마다 사전 공지, 완료 공지 진행을 따로 보여 줍니다. 두 공지를 모두 담당자 확인하면 지난 작업으로 넘어가고, KT 공지가 한쪽만 온 작업은 작업 화면에서 이름을 적고 직접 넘깁니다(되돌리기 가능). 지난 작업은 최근 30일 것만 보이고(그 전 작업은 달력), 끝나지 않은 작업은 오래돼도 진행 중에 남습니다. "새 메일 확인"은 직전 확인 후 10초 안에는 다시 요청하지 않습니다.
- 사전 공지 차수: KT가 같은 사전 공지를 며칠 뒤 다시 보내면(2시간 안의 중복 메일은 같은 발송) 사전 공지 2차, 3차 안내가 따로 생기고, 차수마다 보낸 메일 확인, 담당자 확인을 합니다. 보낸 메일은 KT 발송 시각 기준으로 해당 차수에 붙습니다.
- 표 정렬: 모든 표는 머리글을 누르면 그 열로 정렬되고, 한 번 더 누르면 반대로 정렬됩니다.
- 별도 발송 탭(예: 협력기관): 다른 회사가 대신 안내를 보내는 고객. 그 회사의 발송 주소에서 온 '작업' 메일이 발송 사본이 되어 계정, 공지 종류, 작업 일시로 맞춰집니다. 이 고객은 작업 공지 탭에서 빠지고, 고객 정보가 없어도 확인 필요가 되지 않습니다. 탭 이름, 대상 계정, 발송 주소, 그리고 그 회사 명의 안내문 틀(받는 사람, 참조, 숨은참조, 제목 앞부분, 첫 인사)은 `/admin/`의 "Partner channels"에서 관리합니다(주소는 DB에만 두고 소스에는 넣지 않음). 틀을 채우면 안내 화면에 보내는 사람, 받는 사람(확인 필수)부터 본문까지 복사 칸이 생기고, 바꾼 뒤에는 `prepare_notifications --redraft`로 아직 복사하지 않은 안내문을 다시 씁니다.
- 달력: 월별로 작업이 있는 날과 진행 상황.
- 보낸 안내 메일: 고객에게 보낸 메일 중 메일함으로도 받은 메일과 실제 내용. KT 공지와 보낸 메일은 메일의 HTML 모양(표 포함) 그대로 보여 주고, 바깥 서버의 이미지, 스크립트는 불러오지 않습니다('텍스트로 보기'로 글자만 볼 수 있음).
- 작업 기록: 고객 안내 한 건마다 작업 일시, 작업 내용, 구분(탭), 공지(사전 N차/완료), 고객, 계정, 받는 사람, 상태, KT 공지 수신, 발송 확인, 확인자, 확인 시각, 지난 작업 처리를 한 줄로 남긴 표. 메일 본문은 남기지 않습니다. 새 메일 확인 때마다, 그리고 담당자 확인, 발송 기록, 지난 작업 처리 직후 갱신되며, 1년 뒤 메일과 안내가 지워져도 이 줄은 남습니다. 연도, 월, 구분으로 걸러 **CSV 다운로드**(UTF-8 BOM, Excel에서 바로 열림)할 수 있습니다.
- 확인 필요: 모든 탭(별도 발송 포함, 탭 이름 표시)의 고객 정보에 없는 계정, 발송이 늦은 안내, 내용을 자동으로 읽지 못한 메일 등. 읽지 못한 메일과 작업 공지가 아닌 KT 메일(수작업 요청 문의 등)은 확인한 사람 이름을 적고 골라서 목록에서 뺄 수 있습니다(메일은 지우지 않고, '목록에서 뺀 메일'에서 되돌림).
- 고객 정보: 검색, 수정, 추가, **CSV 다운로드**(지금 검색과 구분 그대로, Excel용 UTF-8). 화면의 CSV 가져오기는 없앴습니다(사용자 2026-10-21; 일반 고객은 운영 DB, 그 밖은 화면에서 입력, 파일 적재는 아래 명령). 고치면 이전 내용은 변경 이력으로 남고, CSV를 다시 가져와도 화면에서 고친 고객은 덮어쓰지 않습니다. 고치면 아직 보내지 않은 안내의 받는 사람과 '확인 필요'를 바로 다시 판정합니다(고객 정보에 없던 계정 → 발송 대기, 보낸 메일의 받는 사람이 고객 이메일과 맞게 되면 발송 추정 → 고객 발송 확인). 수집 때마다도 같은 판정을 합니다.
- 사내 계정(고객 정보 → 사내 계정): 예시클라우드가 쓰는 KT Cloud 계정. 작업은 모아서 보여 주지만 고객 안내를 보내지 않고 발송, 담당자 확인도 하지 않습니다. 고객 계정도 대부분 example.com 주소라 도메인으로 정하지 않고 하나씩 지정합니다. 단 **사내 고객명**(같은 화면)에 넣은 이름(회사명, 없으면 이름; 공백 무시)의 계정은 전부 사내 계정이 되고, 운영 DB나 CSV로 그 이름의 계정이 새로 들어오면 다음 수집 때 자동으로 지정됩니다. 사람이 해제한 계정은 다시 지정하지 않습니다. **안 쓰는 계정**은 운영 DB가 그 계정의 정보를 새로 주거나 바꾸면(5분 수집, '운영 DB 지금 조회') 자동으로 해제되어 다시 고객이 됩니다(해제한 사람 '운영 DB 갱신'). 운영 DB에 그대로 있는 것만으로는 해제하지 않고, CSV 업로드로도 해제하지 않습니다.
- 건의사항: 오류, 개선 의견을 남기고, 상태(접수, 진행 중, 반영 완료, 보류)와 답변을 적습니다. 서버에서는 `manage.py suggestions`로 처리 전 항목을 봅니다.
- 관리(아이디, 비밀번호): 메뉴에는 없고 `http://192.0.2.10/admin/` 으로 직접 들어갑니다.

안내 상태: 확인 필요 → 발송 대기 → 작성 중(복사함, 발송 아님) → 고객 발송 확인(보낸 메일이 메일함에 들어옴) 또는 발송 기록(직접 기록) / 발송 추정(보낸 메일은 있으나 받는 사람에 고객 이메일 없음) → 담당자 확인(이름을 적고 확인). 사내 계정의 안내는 '사내 계정'으로 따로 둡니다. 안내번호는 화면의 작업 정보에만 있고 본문에는 넣지 않습니다(보낸 메일은 계정, 공지 종류, 작업 일시로 확인).

## 회사 운영 DB 조회 (MySQL 뷰)

고객 계정과 연락처를 회사 운영 DB의 뷰(`examplecloud.v_customer_accounts`, 열은 CSV와 같음)에서 읽습니다. 접속 정보는 `/etc/csp-notice/opsdb.env`에만 둡니다(root:cspnotice 0640, 저장소에 넣지 않음):

```
OPSDB_HOST=<IP 또는 호스트>
OPSDB_PORT=3306
OPSDB_USER=<조회 계정>
OPSDB_PASSWORD=<비밀번호>
# 아래 둘은 생략하면 examplecloud / v_customer_accounts
OPSDB_DATABASE=examplecloud
OPSDB_VIEW=v_customer_accounts
```

```bash
chown root:cspnotice /etc/csp-notice/opsdb.env && chmod 0640 /etc/csp-notice/opsdb.env
runuser -u cspnotice -- /data/csp-notice/venv/bin/python /data/csp-notice/release/manage.py opsdb --probe   # 접속, 열 이름, 건수만 출력
```

조회만 합니다(SELECT). 값은 화면 밖으로 출력하지 않습니다.

파일이 있으면 **5분 수집마다** 뷰를 읽어 일반 고객을 갱신하고(내용이 그대로면 건너뜀), 고객 정보 화면의 '운영 DB 지금 조회' 버튼으로 바로 읽을 수도 있습니다. 뷰의 열은 CSV 열로 옮겨 담습니다(`cloud_account`→account, `company`→회사명, `manager`→담당자, 휴대전화 `phone1-2-3`→phone, 없으면 사무실 `tel1-2-3`). 뷰에 있는 계정은 **운영 DB가 기준**이라 화면에서 고친 값이 있어도 DB 값으로 바뀌고(이전 값은 변경 이력에 남음), 그 고객 화면은 읽기만 됩니다 — 고칠 건 운영 DB에서 고치면 5분 안에 반영됩니다. 뷰에 없는 계정(화면에서 추가한 일반 고객)과 공공 고객은 건드리지 않습니다. 특정 계정을 운영 DB와 상관없이 화면에서만 관리하려면 고객 화면에서 **웹에서만 관리**를 켭니다(운영 DB 고객은 '웹에서만 관리로 전환' 버튼). 그 계정은 뷰에 있어도 DB 값으로 바뀌지 않습니다(예: 기관A 계정). 조회 결과(시각, 건수, 실패 사유)는 고객 정보 화면에 보이고, 실패해도 메일 수집은 계속됩니다. 명령: `manage.py opsdb --sync`.

## 자동 발송 (NCP SENS 메일)

KT 공지를 받으면 '발송 대기'인 고객 안내를 사이트가 NCP SENS로 바로 보냅니다(사전 공지 2차, 3차 포함, 별도 발송 고객 제외). 설정은 `/etc/csp-notice/sens.env`에만 둡니다(root:cspnotice 0640, 저장소에 넣지 않음):

```
NCP_ACCESS_KEY=<서브 계정 Access Key>
NCP_SECRET_KEY=<Secret Key>
SENS_MAIL_SERVICE_ID=ncp:mail:kr:<숫자>:<프로젝트>
MAIL_SENDER_ADDRESS=system@example.com
MAIL_SENDER_NAME=ExampleCloud
MAIL_CC=<참조 주소>        # live만: 지금 공지의 참조와 같게
MAIL_BCC=<사내 사본 주소>   # live만: 지금 공지의 숨은참조(수집 메일함으로 들어오는 주소)와 같게
SEND_MODE=on              # off면 이 서버는 발송하지 않음(예행연습, 백업 복원). 켜고 끄기는 화면 '환경 설정'
MAIL_TEST_TO=<테스트 주소> # (선택) 테스트 모드의 받는 사람. 화면 버튼은 2026-10-22에 뺌
```

- 본문: 회사 메일 양식(`notifications/mail_template.html`, 지금까지 나간 공지 86통과 같은 양식)의 `__CONTENT__` 자리에 안내 초안을 줄마다 `<br />`로 넣습니다. 양식을 바꾸면 이 파일을 고쳐 배포합니다.
- 보내는 시점: 5분 수집에서 메일함을 읽고 사본을 대조한 **다음**. 그 사이 직접 보낸 안내는 사본이 들어와 '발송 대기'가 아니게 되므로 다시 보내지 않습니다.
- 같은 안내는 한 번만: 진행 중, 응답 대기, 접수, 완료된 시도가 있으면 DB가 두 번째 시도를 거부합니다. 응답이 없던 요청은 SENS 발송 목록에서 본문까지 같은 요청을 찾아 확인한 뒤에만 다시 보냅니다. SENS가 접수한 메일은 다시 보내지 않습니다.
- 실패: 접수가 안 된 실패(연결 거부, 호출량 초과)는 5분 뒤 다시, 3번 연속이면 '발송 실패'. 고쳐지지 않는 실패(잘못된 값)와 SENS의 전달 실패는 바로 '발송 실패'. 확인 필요에 나오고, 안내 화면의 **발송하기**로 다시 보냅니다(메일함을 다시 읽은 뒤 발송). 키, 권한, 월 한도 문제는 횟수에 세지 않고 발송을 멈추며 대시보드에 표시합니다.
- 결과: SENS 완료 → 고객 발송 확인, 일부 실패 → 발송 추정, 실패 → 발송 실패. BCC 사본이 메일함에 들어오면 지금처럼 사본으로도 확인됩니다.
- 켜기 전에 만들어진 안내도 아직 안 보냈으면 SENS 확인을 거쳐 자동으로 보냅니다. KT 메일이 하루 넘게 지난 것, 작업이 끝난 사전 공지는 자동으로 보내지 않습니다.
- 안내 화면의 **발송하기**는 자동 발송이 보내지 않는 안내(발송 실패, SENS 보류, KT 메일 하루 지남, 작업 끝난 사전 공지, 작성 중)에만 보입니다. 곧 자동으로 나갈 안내에는 '다음 수집 때 자동 발송'만 보입니다. 테스트 발송 버튼은 없습니다(사용자 2026-10-22).
- **켜고 끄기**: 화면 **환경 설정 > 자동 발송**에서 **ON / OFF**(이름 필수, 변경 이력 표시; 테스트 모드는 없음, 사용자 2026-10-21). 아무도 켜지 않았으면 OFF. `sens.env`가 `SEND_MODE=off`면 ON을 고를 수 없습니다. ON으로 켤 때마다 그 뒤에 만들어진 안내만 자동으로 보냅니다. ON일 때는 '발송 대기'인 안내에도 **발송하기**가 있어(OFF 동안 온 안내 등) 사람이 골라 보낼 수 있습니다.
- **보내기 전 확인 (규칙 6)**: 자동, 발송하기, 테스트 모두, 보내기 직전에 SENS 발송 목록에서 KT 메일 이후 같은 받는 사람, 같은 제목으로 사이트가 보내지 않은 메일(손 발송)을 찾습니다. 있으면 보내지 않고 '발송 실패'(사유: SENS에 같은 메일 있음)로 확인 필요에 올립니다. 사본이 들어오면 그대로 고객 발송 확인이 되고, 다른 안내의 메일이었으면 **발송하기**로 보냅니다(이미 본 메일은 건너뛰고 그 뒤 새 메일만 다시 확인). 확인 조회가 실패하면 보내지 않고 실패 1회로 셉니다.
- **백업 DB로 되돌리거나 서버를 옮길 때는 먼저 `SEND_MODE=off`**: 되돌린 DB는 그 뒤에 보낸 기록을 모르므로 다시 보낼 수 있습니다. 화면의 선택보다 이 파일이 우선합니다.

## 별도 발송 받는 사람 그룹

협력기관처럼 별도 발송 고객은 탭의 **받는 사람 그룹**에서 시스템별 받는 사람, 참조, 서버를 관리합니다. KT 공지의 대상 서버가 모두 그룹에 있으면 그룹마다 안내가 하나씩 만들어지고, 서버가 없거나 그룹에 없는 서버가 있으면 전체 받는 사람에게 1건이 갑니다(그룹에 없는 서버는 확인 필요에 표시, 그룹에 넣으면 아직 손대지 않은 안내는 다시 나뉨). KT가 다른 이름으로 쓰는 서버는 'KT 공지 이름 = 서버 목록 이름'으로 적습니다.

## KT 공지 양식 (환경 설정)

KT가 공지 메일 형식을 바꾸면 관리 계정이 화면 **환경 설정 > KT 공지 양식**에서 고칩니다(회의 건의사항 2026-10-20; 메인 아이디에는 보이지 않음, 2026-10-22). 네 단계로 보여 줍니다: 1 KT가 보내는 주소, 2 제목으로 공지 종류 나누기(공지 종류마다 제목에 있는 말과 예), 3 본문에서 읽는 항목(KT 메일에 적힌 이름, 대상 계정과 작업 내용과 작업 일시는 필수, 공백 무시, 쉼표로 여러 개, 쓰임), 4 고객 안내에서 빼는 KT 꼬리말. 기본값은 실제 메일에서 읽은 규칙입니다(`mailcollect/ktform.py`).

KT 장애 공지(사용자 2026-10-22): 제목에 'Down 발생'이 있으면 장애 발생, 'Down 복구'가 있으면 장애 복구 공지로 받습니다(같은 화면에서 단어 변경, 비우면 받지 않음). 발생과 복구는 작업 한 건(`Work.incident`, 작업 목록에 '장애' 표시)의 두 단계가 되고, 고객 안내는 KT 제목 그대로 `[예시클라우드] 컴퓨팅 노드 Down 발생 안내` / `... 복구 안내`로 만들어져 자동 발송이 ON이면 바로 나갑니다(사내/안 쓰는 계정 제외). 안 나간 장애 안내는 KT 메일 1시간 뒤 '발송 늦음'.

KT 작업 연기 공지(2026-10-25): 제목에 '연기'가 있으면(`[kt cloud 작업 연기 공지]`, 같은 화면에서 단어 변경) 작업일시가 '추후에 안내 예정'처럼 시각이 없어도 같은 제목, 같은 계정의 작업(30일 안에 시작)에 붙어 그 작업 사전 공지의 한 차수가 되고, 화면에는 '작업 연기 공지'로 보입니다. 고객 안내는 `[예시클라우드] 작업 연기 공지 안내`(첫 문장 '... 연기 공지가 수신되어 안내드립니다.')로 만들어져 작업 시간이 지났어도 자동 발송되고, 안 나가면 KT 메일 1시간 뒤 '발송 늦음'. 그 사본(같은 제목)은 작업 제목으로 연기 공지 안내에 붙습니다. 붙을 작업이 없고 날짜도 없으면 확인 필요.
연기된 작업은 원래 일정을 그대로 두고 목록, 작업 화면, 달력, 안내 화면에 '연기'와 '다음 일정'(KT가 쓴 그대로, 예: 추후에 안내 예정)을 보여 주며 진행 중에 남습니다. KT가 같은 제목의 작업 공지를 새 날짜로 보내면 그 작업이 재작업(`Work.rework_of`, '재작업' 표시)이 되고 연기된 작업은 지난 작업으로 넘어갑니다. 안내 화면 아래 'KT 공지 원문'에서 그 고객에게 온 이 작업의 KT 메일을 시간순으로 펼쳐 봅니다.
KT 서비스 점검 요청 공지(2026-10-27): 제목에 '점검 요청'이 있으면(`[KT cloud 서비스 점검 요청 공지]`, 같은 화면에서 단어 변경) 장애 공지처럼 다룹니다. 제목이 작업 이름('서비스 점검 요청'), 메일 시각이 시작이고, 안내는 `[예시클라우드] 서비스 점검 요청 안내`(첫 문장 '... 서비스 점검 요청 공지가 수신되어 안내드립니다.')로 바로 자동 발송, 안 나가면 1시간 뒤 '발송 늦음'. KT가 뒤이어 보내는 메일이 없어 완료 단계가 없는 작업이고(목록의 완료 칸 '-', '점검 요청' 표시), 안내를 담당자 확인하면 지난 작업으로 넘어갑니다.

- **미리보기**: 저장 전에 최근 30일 KT 공지를 지금 양식과 고친 양식으로 각각 읽어 항목별 건수, 분류가 바뀌는 메일, 모르는 항목 이름을 보여 줍니다.
- **저장**: 이름 필수, 저장 이력이 남고 언제든 **기본값으로** 되돌릴 수 있습니다. 다음 수집부터 새 메일에 적용됩니다. 꼬리말이 바뀌면 아무도 복사하지 않은 초안을 다시 씁니다.
- **확인 필요 KT 공지 다시 읽기**: 최근 30일 KT 공지 중 문제가 있던 것(양식이 안 맞아 못 읽은 공지)만 저장된 양식으로 다시 읽습니다. 작업 없이 만들어졌던 고객 안내는 찾은 작업에 붙고, 공지 문제만이 사유였으면 '발송 대기'가 됩니다. 이미 작업과 고객 안내가 있는 공지와 잘 읽힌 공지(KT의 쌍둥이 메일 포함)는 다시 읽지 않습니다(같은 고객에게 안내가 두 번 생기지 않게).
- **KT 기타 메일 다시 분류**: 제목 규칙이 안 맞아 'KT 기타'(헤더 저장 안 함)로 분류된 최근 하루 메일을 다음 수집에서 TOP으로 다시 분류합니다.

## 메일 수집 (수신 전용)

`/etc/csp-notice/pop3.env`의 계정으로 접속해 새 메일의 헤더를 읽고 분류한 뒤, 확정 분류(KT 공지 4종, 예시클라우드 사본 2종)만 본문을 받습니다. 서버의 메일은 삭제, 이동, 수정하지 않습니다.

정기 실행은 systemd가 맡습니다 (5분 주기, `cspnotice` 계정).

journalctl -u csp-notice-scan.service -n 20       # 최근 실행 결과
```

지금 바로 한 번 수집하려면 (웹의 "지금 확인" 버튼도 같은 방식, 직전 수집 후 10초 안에는 생략):

runuser -u cspnotice -- /data/csp-notice/venv/bin/python manage.py request_scan
```

운영 DB는 서비스 계정으로 다룹니다: `runuser -u cspnotice -- /data/csp-notice/venv/bin/python manage.py ...`

### 메일함 추가 (알림 메일함 등)

`/etc/csp-notice/mailboxes/<이름>.env` 파일 하나가 메일함 하나입니다. 추가 메일함은 기본으로 **KT 작업 공지만** 저장하고(`COLLECT=kt`; 예시클라우드 사본, 기타 메일은 건수만), 처음 켤 때는 최신 2000통만 읽고 그 이전 메일은 건너뜁니다(`BACKFILL`). 파일을 만들면 **꺼진 상태로 등록**되므로, 크기를 확인한 뒤 켭니다.

```bash
# 1) 파일 작성 (비밀번호는 이 파일에만)
install -m 0640 -o root -g cspnotice /dev/null /etc/csp-notice/mailboxes/alarm.env
vi /etc/csp-notice/mailboxes/alarm.env
#   LABEL=알림 메일함
#   POP3_USER=계정@example.com
#   POP3_PASSWORD=...
# 2) 크기 확인 (로그인 → STAT → 종료, 메일은 읽지 않음), 3) 켜기, 4) 상태
runuser -u cspnotice -- /data/csp-notice/venv/bin/python manage.py mailboxes --probe alarm
runuser -u cspnotice -- /data/csp-notice/venv/bin/python manage.py mailboxes --enable alarm
runuser -u cspnotice -- /data/csp-notice/venv/bin/python manage.py mailboxes
# 5) (선택) 처음에 건너뛴 이전 메일도 읽기: 최신순, 수집 1회당 500통
runuser -u cspnotice -- /data/csp-notice/venv/bin/python manage.py mailboxes --read-skipped alarm
```

서버에서 사라진 지 30일이 지난, 저장하지 않은 메일의 기록(UIDL, 분류)은 수집 때 정리합니다.

같은 메일(Message-ID가 같은 메일)은 한 번만 저장합니다. 다른 메일함에서 이미 받았거나, 두 주소로 와서 한 메일함에 두 번 들어온 메일은 '이미 받은 메일'(`duplicate`, UIDL, 분류만)로 기록하고 본문을 읽지 않습니다.

### 메일함 교체 (여러 메일함 → 전달받는 메일함 하나)

수집 메일함은 파일이 정합니다: 기본 메일함 `/etc/csp-notice/pop3.env`(필수) + `mailboxes/*.env`. `pop3.env`를 새 계정으로 바꾸고 다른 파일을 지우면, 다음 수집부터 새 계정만 읽고 파일이 없어진 메일함은 자동으로 꺼집니다(기록은 남음, 대시보드에서도 빠짐). 이미 받은 메일과 같은 메일(Message-ID)은 다시 읽지 않으므로 겹쳐도 됩니다.

```bash
vi /etc/csp-notice/pop3.env
#   LABEL=전달 메일함
#   POP3_USER=계정@example.com
#   POP3_PASSWORD=...
#   BACKFILL=5000        # 처음 한 번만: 최신 5000통(두 주소 합쳐 이틀치 이상)까지 읽음
rm /etc/csp-notice/mailboxes/alarm.env
# 최신 50통의 헤더만 읽어 분류별 건수 확인 (보낸 사람, 제목이 전달 후에도 그대로인지; 이미 받은 메일 수)
runuser -u cspnotice -- /data/csp-notice/venv/bin/python manage.py mailboxes --probe main --sample 50
```

`BACKFILL`은 새 메일함을 처음 읽을 때만 쓰입니다. 그 뒤로는 새로 온 메일을 개수 제한 없이 모두 읽고, 수집 1회(5분)에 헤더 500통, 본문 100통까지(최대 60초) 최신순으로 처리하며 남은 것은 다음 수집에서 이어 읽습니다(2026-10-19~21 가장 많았던 5분: 두 메일함 합쳐 117통).

전달이 '새 메일로 전달'(보낸 사람이 전달한 주소로, 제목 앞에 FW:)이면 KT 공지로 분류되지 않습니다(`--sample`에서 kt_notice 대신 suspect로 보임). 메일 서버의 전달은 원본을 그대로 보내는 방식(리다이렉트)이어야 합니다.

분류 규칙을 바꾼 뒤에는 저장된 헤더를 다시 분류합니다 (메일 서버 접속 없음). `--recheck-other`를 붙이면 헤더를 저장하지 않았던 `other` 메일을 다음 수집 때 다시 읽습니다.

```bash
/data/csp-notice/venv/bin/python manage.py reclassify
```

## 보관 기간 (1년)

매일 밤 백업(`backup_db`)이 끝나면 같은 서비스가 `purge_old`를 실행해 1년(`CSP_KEEP_DAYS`)보다 오래된 작업, 고객 안내, 처리 이력, 메일(서버에서 사라진 것), 수집 기록, 처리 끝난 건의사항을 지웁니다. 고객 정보, 사내 계정, 별도 발송 설정, 그리고 '작업 기록'의 줄(작업 일시, 내용, 고객, 확인자)은 지우지 않습니다. 지우기 직전에 작업 기록을 한 번 더 맞춥니다. 지운 데이터도 14일 동안은 백업에 남습니다. 미리 건수만 보려면:

```bash
runuser -u cspnotice -- /data/csp-notice/venv/bin/python manage.py purge_old --dry-run
```

작업 기록은 수집 때마다 저절로 맞춰지지만 바로 맞추려면 `manage.py sync_records`.

## 건의사항 확인 (서버)

```bash
cd /data/csp-notice/release
runuser -u cspnotice -- /data/csp-notice/venv/bin/python manage.py suggestions          # 처리 전 항목
runuser -u cspnotice -- /data/csp-notice/venv/bin/python manage.py suggestions --all    # 전체
runuser -u cspnotice -- /data/csp-notice/venv/bin/python manage.py suggestions --set 3 --status done --reply "반영했습니다" --by "이름"
```
